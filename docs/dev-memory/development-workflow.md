# Subline 开发与验收流程

Jack 于 2026-10-22 确认：日常迭代先在本地 Dev 完成，范围稳定后再打包与实机验收，最后更新展示截图。

- **迭代**：默认复用现有 Dev 工作树，用热更新验证界面与交互；不要为每次调整重新打包。Dev 身份与隔离约束见 [DEV-VARIANT](../../apps/macos/DEV-VARIANT.md)。
- **检查**：按改动范围选择相关检查，由一个负责人统筹。Agent 之间共享同一提交、同一工作树内容下的检查结果与命令；后续只重跑受新改动影响或先前失败的检查。仓库、CI 和任务明确要求的门禁仍须全部满足。
- **打包**：范围稳定后打包一次；现有打包命令已包含 build，不在它之前重复构建。若代码或打包输入随后改变，须更新产物并重验受影响项。源码进入产物的约束见 [workspace-build](workspace-build.md)。
- **安装验收**：在实际安装的 Dev 中验证原问题、设置持久化，以及本次涉及的关键平台路径。分发或修改 macOS 生命周期时，仍执行相应的完整门禁、签名、公证与安装验收；正式版仅在当前授权范围内接入同一份已验证代码。
- **截图**：验收通过后，从实际安装且对应当前代码的应用取图；区分 Dev、正式版与已发布版本的证据。
- **等待与沟通**：使用较长且有界的等待，只在进展、失败或需要行动时更新；避免频繁轮询并重复报告未变化状态。
